# RECOVERY

## 기본 원칙

검증 실패 시 광범위한 수정 전에 원인을 진단한다. 요구사항이나 검증을 약화해 통과한 것처럼 만들지 않는다. UI 변경은 기존 design token, 공통 관리자 form pattern, 반응형 레이아웃을 우선 보존한다.

## 실패 루프

1. 실패 출력과 브라우저 console, network, 접근성 정보를 끝까지 읽는다.
2. 실패 유형을 구현 버그 / 잘못된 테스트 / 의존성 / 환경 / 요구사항 불명확 / scope 충돌 / 레거시 데이터 손실로 분류한다.
3. PRD.md, PLAN.md, VALIDATION.md와 현재 저장 전후 payload를 비교한다.
4. 가장 작은 가역 변경 1회를 적용한다.
5. 가장 작은 관련 검증부터 재실행한다.
6. 데스크톱·모바일 중 영향 viewport를 다시 확인한다.
7. PROGRESS.md를 업데이트한다.

## 재시도 한계

같은 blocking condition 또는 validation failure가 서로 다른 3회 시도 후에도 반복되면 자체 수정을 멈추고 사용자·제품 결정을 요청한다.

다음을 PROGRESS.md에 기록한다.

- 실패한 명령 또는 기준
- 시도한 세 가지 변경
- 각각의 실패 이유
- 가장 안정적인 상태
- 다음으로 안전한 옵션

Codex Goal을 blocked로 표시하는 것은 같은 blocker가 최소 3개의 연속 Goal turn에서 반복되고 안전한 진전이 불가능할 때로 제한한다.

## scope 잠금

- 무관한 모듈 재작성 금지
- PLAN.md에 없는 public API 변경 금지
- DB schema와 Supabase migration 변경 금지
- 기존 행사 slug 일괄 변경 금지
- 기존 위치 메타데이터와 `official_url` 삭제·초기화 금지
- 자동 지오코딩, 지도 SDK, 장소 폼 재설계 추가 금지
- 테스트·검증 삭제 또는 skip 금지
- 검증 명령을 더 약한 명령으로 교체 금지
- 이해 없이 오류 침묵 처리 금지
- 좁은 폼 UX 문제를 전역 design system refactor로 해결 금지
- 기능 검증만으로 수동·시각 검증을 대체하지 않기
- 사용자 소유 `design-qa.md`, `output/`, 실행 중 개발 서버를 명시적 승인 없이 변경·종료하지 않기

## 방향 재확인 규칙

접근법을 바꾸기 전에 Goal 문장, PRD Non-goals, 현재 마일스톤, 새 변경의 직접 기여 여부를 다시 확인한다. 지도 선택기, URL migration, DB 컬럼 제거가 필요해 보이면 현재 구현을 멈추고 기존 주소 검색 fallback과 데이터 보존 방식으로 해결할 수 있는지 먼저 확인한다.

## 되돌리기 규칙

자신의 마지막 실패 변경만 되돌린다. 사용자 변경은 명시적 지시 없이 절대 되돌리지 않는다. 데이터 보존 회귀가 발견되면 새 저장을 중단하고 테스트용 데이터에서 원인을 재현한 뒤 최소 payload 변경으로 복구한다.
