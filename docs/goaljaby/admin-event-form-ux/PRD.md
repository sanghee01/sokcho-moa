# PRD — 행사 작성·수정 폼 UX 개선

## 문서 상태

- output_lang: `ko`
- 작업 유형: `ui` (높은 신뢰도)
- 검증 엄격도: `standard`
- artifact_only: `false`
- 대상 저장소: `/Users/sanghee/Documents/develop/sokcho-moa`

## 한 문장 목표

속초모아 운영자가 기술 메타데이터를 직접 다루지 않고도 필수 정보와 공개 화면의 노출 결과를 이해하며 행사를 작성·수정하고, 완료 후 대시보드로 자연스럽게 돌아가게 한다.

## 대상 사용자와 주요 흐름

- 대상 사용자: 행사 정보를 등록·검수하는 속초모아 운영자
- 주요 흐름: 관리자 대시보드 → 새 행사 작성 또는 기존 행사 수정 → 필수·선택 정보를 구분해 입력 → 작성/수정 완료 → 성공 안내가 있는 관리자 대시보드
- 공개 화면 연결: 행사 안내·신청 URL 입력 → 행사 상세의 포스터 옆 CTA 생성 → 중복 링크 없이 방문자가 다음 행동을 선택

## 현재 문제

1. 작성자가 공개 URL용 기술 식별자인 `slug`를 직접 만들고 형식까지 기억해야 한다.
2. 위도·경도와 위치 검증 메타데이터를 직접 입력해야 하는 것처럼 보여 진입 장벽이 높다.
3. 위치 확인일과 마지막 확인일은 내부 신뢰 메타데이터인데 일반 작성 항목처럼 노출된다.
4. 실제 저장에 필요한 항목과 선택 항목의 시각·접근성 구분이 없다.
5. `공식 안내 URL`과 `공식 원문 URL`의 역할이 겹치며, 공개 상세의 CTA와 `관련 링크`도 같은 링크를 반복한다.
6. 운영일정이 한 줄 입력이라 여러 일정의 줄바꿈 작성과 공개 표시가 어렵다.
7. 저장 뒤 수정 화면에 머물러 다음 관리 작업으로 이어지는 흐름이 끊긴다.

## 제품 결정

### slug

- `slug`는 공개 상세 URL을 안정적으로 유지하기 위한 시스템 식별자다.
- 작성 화면에서는 입력란을 제거한다.
- 새 행사는 서버에서 `event-${crypto.randomUUID()}` 형태로 자동 생성한다. 숫자나 문자열을 작성자가 정할 필요가 없다.
- 기존 행사를 수정할 때는 기존 `slug`를 그대로 유지해 이미 공유된 URL을 바꾸지 않는다.

### 위치 정보

- 작성자가 입력하는 위치 정보는 `장소명`과 `주소`까지로 제한한다.
- `위도`, `경도`, `위치 근거 URL`, `위치 확인일`은 작성 화면에서 제거한다.
- 기존 행사의 좌표·위치 근거·위치 확인 시각은 다른 정보를 수정해도 삭제하거나 새 시각으로 덮어쓰지 않는다.
- 새 행사는 좌표 없이 저장할 수 있고, 공개 화면은 현재의 주소 기반 네이버 지도 검색과 지역 단위 주변 명소 fallback을 사용한다.
- 자동 지오코딩이나 지도 선택기는 이번 scope에 포함하지 않는다.

### 확인 시각

- `마지막 확인일` 입력란을 제거한다.
- 행사 저장 시 서버 시각을 `events.last_verified_at`과 해당 출처의 `event_sources.last_checked_at`에 자동 기록한다.
- 위치 확인 시각은 위치를 실제로 다시 검증하지 않는 한 자동 갱신하지 않는다.

### 필수·선택 입력

- 폼 시작에 `* 표시는 저장에 필요한 항목입니다.`를 안내한다.
- 저장 필수 항목인 행사명, 카테고리, 참여 대상, 출처 기관, 행사 안내 URL의 label 또는 legend에 시각적 `*`와 스크린리더용 `필수` 설명을 함께 제공한다.
- 브라우저 `required`와 서버 Zod 검증을 같은 필수 계약에 맞춘다. 참여 대상은 한 개 이상 선택해야 한다.
- 별표가 없는 항목은 선택 입력으로 이해할 수 있게 하고, 조건부 입력은 해당 영역 설명으로 조건을 밝힌다.

### 링크와 공개 버튼

- 수동 작성 폼의 `공식 안내 URL`과 `공식 원문 URL`을 `행사 안내 URL *` 한 개로 통합하고 기존 `sourceUrl`에 저장한다.
- `행사 안내 URL`은 기관 홈이나 목록이 아니라 해당 행사를 직접 설명하는 공식 상세 페이지이며, 공개 상세의 `행사 안내` CTA로 노출된다는 설명을 붙인다.
- `신청·예매 URL`은 선택 항목이며 값이 있을 때만 `신청·예매` CTA를 만든다고 설명한다.
- `공유하기` 버튼은 입력값과 무관하게 시스템이 항상 만든다고 설명한다.
- 기존 `official_url` 데이터는 삭제하지 않지만 수동 폼과 공개 링크 선정에서 더 이상 사용하지 않는다.
- 포스터 옆 CTA는 `신청·예매`(URL이 있을 때), `행사 안내`(항상), `공유하기`(항상)로 구성한다.
- 핵심 정보의 `관련 링크` 행은 포스터 옆 CTA와 중복되므로 제거한다. JSON-LD의 대표 URL도 `sourceUrl`을 사용한다.

### 운영일정

- `운영일정`을 여러 줄 `textarea`로 바꾸고 예시도 여러 줄로 제공한다.
- 저장한 줄바꿈은 `formatOperatingSchedule`에서 줄 단위로 보존하며 각 줄 내부의 불필요한 연속 공백만 정리한다.
- 공개 상세의 운영일정 값은 `whitespace-pre-line`에 해당하는 표현으로 줄바꿈을 보여준다.

### 정보 구조와 완료 이동

- 긴 단일 폼을 `기본 정보`, `일정·신청`, `장소·요금`, `링크·출처`, `노출 설정`의 의미 단위로 나눈다.
- 각 구역에 짧은 설명을 두고 기존 design token, 입력 컴포넌트 모양, 반응형 1열/2열 패턴을 유지한다.
- 제출 버튼은 신규 `작성 완료`, 수정 `수정 완료`로 문맥에 맞게 표시한다.
- 신규 작성과 기존 수정이 성공하면 모두 `/admin?saved=event-created` 또는 `/admin?saved=event-updated`로 이동하고 대시보드 상단에서 성공 메시지를 보여준다.

## 완료 기준

- **AC-1**: 새 행사 폼에 보이는 `slug` 입력이 없고 서버가 유효한 고유 slug를 자동 생성하며, 기존 행사 수정은 기존 slug를 유지한다.
- **AC-2**: 위도·경도·위치 근거 URL·위치 확인일 입력이 보이지 않고, 수정 저장 전후 기존 위치 메타데이터가 동일하며 새 행사는 이 값 없이 저장할 수 있다.
- **AC-3**: 마지막 확인일 입력이 보이지 않고, 성공한 저장 시 행사와 출처의 확인 시각이 같은 서버 기준 시각으로 자동 기록된다.
- **AC-4**: 저장 필수 항목에 접근 가능한 `*` 표시가 있고 브라우저·서버 필수 검증과 일치하며, 선택 항목은 필수로 오인되지 않는다.
- **AC-5**: 폼에는 `행사 안내 URL *`와 선택 `신청·예매 URL`만 노출되고, 각 값이 공개 CTA를 언제 만드는지와 공유 버튼이 자동이라는 설명이 있다.
- **AC-6**: 공개 상세의 포스터 옆에는 조건에 맞는 `신청·예매`, `행사 안내`, `공유하기`만 한 번씩 나타나며 중복 `관련 링크` 행과 `공식 안내/공식 원문` 구분은 사라진다.
- **AC-7**: 운영일정을 여러 줄로 입력·저장할 수 있고 공개 상세에서도 줄바꿈이 보존된다.
- **AC-8**: 새 행사 작성과 기존 행사 수정 성공 후 대시보드로 이동하고 각각 맞는 성공 메시지를 보여준다.
- **AC-9**: 폼이 의미 단위 구역으로 재구성되고 데스크톱·모바일에서 잘림·가로 넘침 없이 키보드와 스크린리더로 label, legend, 도움말, 제출 상태를 이해할 수 있다.

## 구현 scope

- 관리자 행사 폼의 정보 구조, label, 도움말, 필드 노출, 제출 CTA
- 행사 저장 action의 slug·확인 시각 자동화, 숨긴 레거시 위치·공식 URL 데이터 보존, 성공 redirect
- 관리자 대시보드의 작성/수정 성공 메시지
- 공개 행사 상세의 CTA·관련 링크 정리와 운영일정 줄바꿈 표시
